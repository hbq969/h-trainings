02

平台定位与解决的问题

异构日志源统一接入

Kafka、Syslog 等多种日志源，需要一个统一的接入层

日志格式千差万别

不同系统的日志格式各异，需要规则驱动的可配置解析

业务场景差异大

DDoS防护、安全审计等不同场景需要不同处理逻辑，插件化扩展是刚需

运维需要可视化管理

规则配置、实例监控、在线测试需要统一管理界面

06

处理层：一条日志的完整旅程

1正则字段提取 — LogField.regex → Pattern → Matcher，多字段捕获组拼接
2脚本二次加工 — ScriptService.execute()，支持 Python / JavaScript
3模板填充 — StrUtils.replacePlaceHolders() 将字段值填入 formatTemplate
4资产富化 — ResourceRich.rich()，如 IP 反查归属信息
5丢弃过滤 — ChainRule 规则引擎 + 时间段窗口
6自定义处理 — CustomDealFacade.consume() 路由到扩展实现
7输出 Kafka — KafkaTemplate.send() 发送到目标 Topic

入口: DefaultCommonDeal.deal(msg, matchLogRule, ruleBox, kafkaTemplate)

07

规则引擎：三层规则模型

ServerRuleEntity

采集服务实例规则

  • 采集源类型 & 端口
  • 匹配策略 (matchWay/regex/script)
  • 丢弃策略 & 调试开关

LogRuleEntity

日志解析规则

  • 正则模板 & 格式模板
  • 富化开关 (richWay)
  • 关联字段列表

KafkaRuleEntity

Kafka 连接规则

  • 源 Kafka 消费配置
  • 目标 Kafka 生产配置
  • 并发/序列化等参数

RuleBox 聚合三层规则 → ruleBoxSet() 热更新 → 无需重启

插件化扩展：CustomDeal 机制

AbstractCustomDeal<T> 基类能力

  • 内置内存队列（有界/无界可配）
  • 单线程 / 多线程消费模式
  • 优雅关闭：drain 队列残留消息
  • CustomDealFacade 按 getKey() 路由

扩展只需两步

// 1. 继承抽象基类，指定消息类型
class TrafficCleanDeal extends AbstractCustomDeal<TrafficCleanModel> {
  // 2. 实现 consumeAsync + getKey + getType
  @Override consumeAsync(TrafficCleanModel msg) { /* 业务逻辑 */ }
  @Override getKey() { return "log-189"; }
}

DDoS 实例：TrafficCleanDeal 业务流

从 Kafka 日志 → 用户通知的完整链路

1Kafka 接收流量清洗汇总日志
2核心引擎解析 → 提取 destIp、poolId、zoneName 等字段
3consumeAsync 触发: 去重判断 → 云网接口查用户ID → IP匹配
4发送短信/邮件通知 (MessageCenterService)
5保存清洗记录 + 通知历史

getKey() → "log-189" 与采集规则中 LogRule 名称匹配
